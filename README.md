# 闪烁码传输（Flicker Transport）

用一块屏幕和一个摄像头，在**没有任何网络连接**的两台设备之间传文件。

发送端把文件编码成一串类似二维码的图案循环闪烁，接收端用摄像头拍下来还原。
纯前端、零第三方依赖、可完全离线运行。

```
┌─────────────┐        闪烁的码图         ┌─────────────┐
│  发送端屏幕  │  ▓▒░▓ ░▓▒░ ▒░▓▒  ─────▶  │ 接收端摄像头 │
│  send.html  │      10~15 fps            │  recv.html  │
└─────────────┘                           └─────────────┘
        单向、无反馈信道 —— 所以用喷泉码，丢帧不需要重传
```

---

## 快速开始

```bash
node server.js
```

浏览器打开 <http://localhost:8000>。

- **两台设备**：一台开 `send.html` 选文件，另一台开 `recv.html` 对准屏幕。
- **只有一台**：开 `loopback.html`，它会模拟一个「假摄像头」把整条链路跑一遍。
- **想用手机摄像头**：见下面的 [HTTPS](#手机当接收端需要-https)。

没装 Node 的话 `python server.py` 也行（只有 HTTP）。

跑算法自测：

```bash
node test/selftest.js
```

## 核心设计

### 为什么用喷泉码，而不是顺序轮播

屏幕→摄像头是一条**纯单向、会随机丢帧**的信道：接收端没法告诉发送端「第 37 帧我没拍到」。
按 1…K 顺序播放的话，漏一帧就得等下一整轮，而下一轮同样会漏帧，收敛极慢。

这里用 **LT 喷泉码（Luby Transform）**：把文件切成 K 个块之后，每帧随机挑若干块异或在一起发出去，
可以无限生成互不重复的编码帧。接收端攒够任意约 **1.3 倍 K** 个有效帧（实测值，
小 K 时偶尔到 2×），用剥离法（peeling）就能反解出全部原始块。

于是：**丢帧无所谓，中途接入无所谓，不需要反向信道，也永远不用「等下一轮」。**

发送端与接收端靠同一个 4 字节 seed 复现出完全相同的块组合，所以帧里只需要带这个 seed。
另外约定 `seed < K` 时退化为系统码（直接就是第 seed 个源块），这样理想情况下前 K 帧就能收完。

### 每帧自带纠错，读错的帧直接丢

- **帧头**：16 字节数据 + RS(32,16) 纠错（可纠 8 字节错）+ CRC16。散布在整幅图上，恒用黑白 1bit 编码——
  因为要先读出帧头才知道这帧用的是哪套调色板，不能自己依赖自己。
- **载荷**：按 255 字节切块做 Reed-Solomon 编码，然后**交织**输出。
  画面上一小片反光造成的连续错误会被摊到所有纠错块上，而不是打爆某一块。
- **兜底**：载荷带 CRC32。RS 有极小概率误纠，CRC32 挡住它。

任何一层没过，这帧就被丢弃——对喷泉码来说那只是一次擦除，无所谓。

### 识别流程

```
摄像头画面
  → 灰度 → Bradley-Roth 自适应二值化（积分图，抗暗角与整体明暗）
  → 扫描 1:1:3:1:1 游程找四角定位图案（QR 式，含十字交叉验证）
  → 从候选点里挑出面积最大的凸四边形
  → 单应变换（平面在针孔相机下的映射是精确射影变换，一个单应就够，不需要分片）
  → 猜版面尺寸 n：先用功能格对比度粗排，再拿帧头的 RS+CRC 做最终裁决
  → 每格取 3×3 共 9 个亚像素点双线性插值采样
  → 读四个方向块判断画面转了几个 90°，把矩阵转正
  → 8×8 格分块归一化，消除光照不均和镜头暗角
  → 读帧头 → 读校准带 → 分类数据格
```

**颜色自校准**：四条边上排着已知颜色的校准格。接收端用它们最小二乘拟合出每个通道的
`观测 ≈ gain × 理想 + bias`，也就是现场学出「这台摄像头把红色拍成了什么」。
所以偏色、白平衡漂移、屏幕色温不一致都不影响判读。

### 一帧长什么样

```
┌──────┬────────────────────┬──────┐   n×n 格，n 为 33~129 的奇数
│ 定位 │     校准带(上)      │ 定位 │
├──────┘                    └──────┤   四角：7×7 定位图案 + 1 格白色分隔带
│ 校  ▣ 方向块         数据    校  │   方向块：4 个 3×3，只有左上是黑的
│ 准         ┌─────┐          准  │   对齐图案：正中 5×5，用于校验单应可信度
│ 带         │对齐 │          带  │   校准带：四边各一排已知颜色的格子
│ (左)       └─────┘         (右) │   帧头格：256 个，等间隔散布在数据区里
├──────┐                    ┌──────┤
│ 定位 │     校准带(下)      │ 定位 │
└──────┴────────────────────┴──────┘
```

帧头 16 字节：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 1 | 协议版本 |
| 1 | 1 | 调色板 ID（低 3 位） |
| 2 | 2 | fileId — 换文件时接收端据此自动重置 |
| 4 | 3 | K，源块总数 |
| 7 | 2 | blockSize，每块字节数 |
| 9 | 4 | seed，本帧的喷泉码种子 |
| 13 | 1 | nsym，载荷每个 RS 码字的校验字节数 |
| 14 | 2 | CRC16 |

数据流（被切块的那一层）：`"FLK1" | 版本 | 标志 | 内容长度 | 内容CRC32 | 文件名长度 | 文件名 | 文件内容`

## 参数与速率

三套调色板：

| 调色板 | 每格位数 | 说明 |
|---|---|---|
| `bw` 黑白 | 1 | 最稳。任何摄像头、任何光照都能读 |
| `gray4` 四灰阶 | 2 | 不受摄像头色度二次采样影响，但四个灰阶只差 85 级，最挑画质 |
| `rgb8` 八色 | 3 | RGB 立方体八顶点，每个通道仍是二值，判决余量最大；怕反光和强色偏 |

按 nsym=32、10 fps 计算的净速率：

| 版面 | 黑白 | 四灰阶 | 八色 |
|---|---|---|---|
| 49×49 | 1.7 KB/s | 3.5 KB/s | 5.3 KB/s |
| 65×65 | 3.6 KB/s | 7.2 KB/s | 10.8 KB/s |
| 81×81 | 6.0 KB/s | 12.1 KB/s | 18.2 KB/s |
| 97×97 | 8.8 KB/s | 18.0 KB/s | 27.2 KB/s |

实际速率还要乘上喷泉码开销（通常 1.3~1.4×，小文件偶尔到 2×）和丢帧率。

**怎么选**：先试 `rgb8` + 65×65 + nsym=32 + 10fps。
版面格数受限于摄像头分辨率——**每格至少要占摄像头 4~5 个像素**。
手机拍 1080p、码图占满取景框时，65 或 81 比较合适。

## 实测能力边界

`node test/selftest.js` 会用合成的摄像头画面（透视、失焦、噪声、暗角、偏色、旋转）跑一遍，
并测出每个场景**至少需要多强的纠错**才能读出来：

| 场景 | bw | gray4 | rgb8 |
|---|---|---|---|
| 理想正对 | 16 | 16 | 16 |
| 明显斜视角 | 16 | 16 | 16 |
| 失焦 + 噪声大 | 16 | **48** | 16 |
| 暗角 + 偏色 | 16 | 16 | 16 |
| 画面旋转 90/180/270° | 16 | 16 | 16 |
| 码图只占画面 60% 且偏离中心 | 16 | **48** | 16 |

结论：`gray4` 在画质差时明显吃力，需要把纠错拉到 48；`bw` 和 `rgb8` 全场景下 nsym=16 就够。

端到端测试：24 KB 文件、25% 丢帧、透视+模糊+噪声，喷泉码开销 1.15×，逐字节一致。

鲁棒孤子分布的两个参数（`LT_TUNING` 里的 `c` / `delta`）是扫描出来的：
在 K = 10~3000、丢帧 40% 的条件下，各种取值的平均开销只差 3%，
说明约 1.3× 是 LT 码在这个 K 区间的固有开销，不是调参没调好。

## 出问题时怎么办

接收端的取景框会给你线索：

| 现象 | 含义 | 怎么办 |
|---|---|---|
| **没有框** | 没找到四角定位图案 | 拉近、别太斜、等自动对焦稳定、提高屏幕亮度 |
| **红框** | 找到了码图但读不出内容 | 太糊/太小/太快：降帧率 → 减小版面 → 提高纠错 → 换 `bw` |
| **绿框但进度不涨** | 一直在收重复帧 | 正常现象，接近 100% 时会变慢；确认发送端还在播 |
| 识别率低于 50% | 帧率超过摄像头能力 | 把发送端帧率降到 8~10 |

其它：

- **发送端画面停了** —— 浏览器会暂停后台标签页的动画。发送期间让页面保持在前台，建议点全屏。
- **接收端很卡** —— 把「识别分辨率」降到 640。
- **屏幕反光** —— 换 `bw` 调色板，它对反光最不敏感。

## 手机当接收端需要 HTTPS

浏览器只在**安全上下文**下开放摄像头。`http://localhost` 算安全，但手机通过
`http://192.168.x.x` 访问电脑就不算了。

```bash
node server.js --https
```

它会用纯 Node 实现的 X.509 生成器现签一张自签证书（**不需要装 openssl**），
覆盖 localhost 和本机所有局域网 IP，缓存在 `.certs/`。
手机访问 `https://电脑IP:8443`，浏览器提示「连接不安全」时选「高级 → 继续访问」即可。

不想折腾证书的话，也可以反过来：**手机开发送端，电脑用自带摄像头当接收端**。

## 目录结构

```
src/
  util.js       CRC32 / CRC16 / 位流读写 / 确定性伪随机数
  rs.js         GF(256) Reed-Solomon：编解码、分块、交织
  fountain.js   LT 喷泉码：鲁棒孤子分布、编码器、剥离解码器
  format.js     版面定义：调色板、功能图案布局、帧绘制
  protocol.js   数据流封装、帧头、发送端 Transmitter、接收端 Receiver
  raster.js     RGB 矩阵 → 像素（纯计算，Node 与浏览器共用）
  detect.js     图像识别全流程（二值化 → 定位 → 单应 → 采样 → 判读）
  synth.js      信道模拟器：透视 / 模糊 / 噪声 / 暗角 / 偏色
  decode-worker.js  解码 Worker（主线程不支持时会自动退回主线程解码）
  ui.js         浏览器端小工具

index.html      说明与导航
send.html       发送端
recv.html       接收端（摄像头 / 屏幕共享）
loopback.html   单机回环自检

server.js       零依赖静态服务器，--https 自签证书
server.py       没装 Node 时的备用（仅 HTTP）
tools/selfsign.js  纯 Node 的自签 X.509 生成器
test/selftest.js   全流程自测（71 项）
```

`src/` 下除 `ui.js` 和 `decode-worker.js` 外都不依赖 DOM，可直接在 Node 里跑。

## 局限

- **没有加密。** 任何能看到那块屏幕的人都能拍下来完整还原。需要保密请自己先加密再传。
- **速率就这么多。** 几 KB/s 到几十 KB/s。传配置、密钥、文本、小图合适，传视频不合适。
- **没有校验反馈。** 接收端解不出来时，发送端不知道，只能一直播。
- **不做镜像识别。** 隔着镜子拍会失败。
- **摄像头帧率是硬上限。** 发送帧率超过摄像头能稳定拍下的速度，只会白白丢帧。
